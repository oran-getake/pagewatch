# PageWatch 実装手順

## 1. 実装方針

初版は「iPhoneアプリ」「API」「常駐Worker」「定期起動Cron」「PostgreSQL」の5要素で完成させる。

手動確認をAPI内で完了まで待たせると、遅いページや接続失敗がAPI全体へ波及する。このため、APIは確認要求を `check_jobs` に登録してすぐ返し、Workerが実際の取得と比較を行う。

初版で保存するのは、初回本文と変更が起きた時点の本文だけである。変更なしの本文を毎回複製しないため、データ容量の増加を抑えられる。確認結果自体は `check_logs` に残す。

## 2. 実装済みの順序

### 第1工程: データと安全境界

1. 匿名端末トークンを発行する。
2. サーバーにはトークンのハッシュだけを保存する。
3. URLを正規化し、同一端末の重複を防ぐ。
4. DNS解決結果に内部IPが1つでも含まれる場合は拒否する。
5. HTTP/HTTPS、標準ポート、公開IPだけを許可する。

完成確認:

- `POST /api/devices/anonymous` がトークンを返す。
- トークンなしで監視APIを呼ぶと401になる。
- localhost、プライベートIP、認証情報付きURLを登録できない。

### 第2工程: URL登録とジョブキュー

1. 監視対象を `watch_targets` に保存する。
2. 1端末5件の上限を確認する。
3. 登録と同じトランザクションで初回ジョブを作る。
4. 1つの監視対象に対し、`queued` または `running` のジョブは1件だけにする。

完成確認:

- URL登録直後の状態が `pending` になる。
- 二重タップしても確認ジョブが重複しない。

### 第3工程: 取得・抽出・比較

1. robots.txtを確認する。
2. DNSを再確認し、公開IPへ直接接続する。
3. リダイレクト先も同じURL検査に通す。
4. 最大2MB、15秒、3リダイレクトに制限する。
5. script、style、nav、header、footer、広告・Cookie表示候補を除く。
6. 空白を正規化し、SHA-256で本文を比較する。
7. 変更時のみ新スナップショットと差分を保存する。

完成確認:

- 初回確認では基準本文だけを保存する。
- 2回目に本文が同じなら `unchanged` になる。
- 本文が変われば `changed` になり、追加・削除文章を取得できる。

### 第4工程: API

1. 一覧、詳細、変更履歴を取得する。
2. 手動確認は202とジョブIDを返す。
3. ジョブ状態をポーリングできるようにする。
4. 停止時は未処理ジョブを取り消す。
5. 削除時は本文、差分、ログ、ジョブを連鎖削除する。
6. 設定画面から匿名端末と全関連データを一括削除できるようにする。

### 第5工程: SwiftUI

1. 匿名端末トークンをKeychainへ保存する。
2. ホームに状態別一覧、変更件数、最終確認を表示する。
3. URL登録フォームを作る。
4. 手動確認後、ジョブ完了まで最大30秒ポーリングする。
5. 追加・削除文章、変更前後、元ページリンクを表示する。
6. 一時停止、再開、削除、設定画面を実装する。
7. Worker起動時とCron起動時に、10分以上止まった実行中ジョブを回収する。

## 3. ローカル確認

### 3.1 バックエンド

```bash
cd PageWatch
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
export DATABASE_URL=sqlite:///./pagewatch.db
alembic upgrade head
uvicorn app.main:app --reload
```

別ターミナル:

```bash
cd PageWatch
source .venv/bin/activate
export DATABASE_URL=sqlite:///./pagewatch.db
python -m app.worker
```

`http://127.0.0.1:8000/docs` で次の順に確認する。

1. 匿名端末を作る。
2. `Authorize` にBearerトークンを入れる。
3. URLを登録する。
4. Workerが初回確認を完了する。
5. 一覧と変更履歴を確認する。

### 3.2 自動テスト

```bash
python -m unittest discover -s tests -v
python -m compileall app tests
```

### 3.3 iPhone

Macで次を実行する。

```bash
cd PageWatch/ios
brew install xcodegen
xcodegen generate
open PageWatch.xcodeproj
```

DebugのAPIは `127.0.0.1:8000` である。iPhone実機からローカルPCへ接続する場合は、HTTPSの開発URLを用意するか、先にRailwayへAPIを配置する。

## 4. Railway配置

Railwayの1プロジェクト内に次を作る。

| Service | 同じGitHubリポジトリ | Start Command | 公開 |
|---|---:|---|---:|
| API | はい | `alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port $PORT` | はい |
| Worker | はい | `python -m app.worker` | いいえ |
| Cron | はい | `python -m app.jobs.enqueue_due` | いいえ |
| PostgreSQL | Railway Database | Railway管理 | いいえ |

手順:

1. GitHubへ `PageWatch` をpushする。
2. Railwayで新規Projectを作る。
3. PostgreSQLを追加する。
4. 同じGitHubリポジトリからAPI、Worker、Cronの3サービスを作る。
5. 全サービスにPostgreSQLの `DATABASE_URL` を参照させる。
6. 全サービスへ同じ `DEVICE_TOKEN_PEPPER` を設定する。
7. APIだけPublic Networkingを有効にする。
8. APIのHealthcheck Pathを `/health` にする。
9. CronのScheduleを `0 * * * *` にする。
10. Cronが期限到来分を投入して終了することを確認する。
11. Workerログでジョブ処理を確認する。

Cronは1時間ごとに起動してよい。各URLの本当の確認時刻は `next_check_at` で制御するため、日1回・日3回・日6回が同時に扱える。

## 5. App Store前の残作業

1. `ios/Config/Release.xcconfig` のAPI URLを置き換える。
2. XcodeのTeamとBundle Identifierを正式値にする。
3. 設定画面の利用規約・プライバシー・問い合わせURLを置き換える。
4. アプリアイコンとスクリーンショットを作る。
5. 実機でURL登録、バックグラウンド復帰、通信断、削除を確認する。
6. TestFlightで外部通信と表示崩れを確認する。
7. 対象サイトの利用規約、自動取得可否、著作物表示量を確認する。
8. App Store Connectのデータ利用申告を実態と一致させる。

## 6. 公開判定

コード完成と公開可能は同じではない。次の4点が揃ったときに初版公開可能とする。

- RailwayのAPI・Worker・Cron・PostgreSQLが継続稼働している。
- 代表5サイトで7日間、誤検知と取得失敗を記録した。
- TestFlight実機試験を完了した。
- 法務ページとApp Store申告が実装と一致した。
